# Submission evidence checklist

**Current status: not built, not submitted.** Registration was already recorded in the private tracker. This repository does not establish a contest entry or any award.

## Before a future final-submit decision

- [ ] Recheck official rules, deadline and any organizer updates.
- [ ] Verify personal eligibility and rights to all content/dependencies.
- [ ] Record only this project's work performed in the permitted window.
- [ ] Confirm the hosted app works from an ordinary fresh browser.
- [ ] Confirm real Buffer OAuth, not a personal-key substitute.
- [ ] Demonstrate successful API editing and read-back with authorized drafts.
- [ ] Verify the exact scopes, redirect URI and public privacy/contact information.
- [ ] Review security, failure cases, unsupported-content exclusions and limitations.
- [ ] Verify ongoing availability during judging; plan through 7 December unless clarified.
- [ ] Prepare a truthful demo no longer than two minutes.
- [ ] Prepare approximately 300 words explaining problem, audience, API use and next steps.
- [ ] Include the actual app client ID where the official form asks; never the client secret.
- [ ] Review promotional licence and other applicable terms with the user at action time.
- [ ] Get authorization for final submission and any personal data the form requires.
- [ ] Save the actual entry receipt/URL and time after submission; do not infer success from a click.

## Evidence needed for each claim

| Proposed claim | Acceptable evidence | Not enough |
| --- | --- | --- |
| Connects to Buffer | Successful real OAuth and authorized API read | Login-styled button or personal key |
| Repairs linked facts | Exact before/after draft text and read-back | Local animation/sample data |
| Preserves surrounding writing | Character-level comparison in supported cases | Visual intuition alone |
| Detects stale baselines | Controlled external edit and refused old approval | A hardcoded amber card |
| Works across two channels | Genuine successful flow on both | Two icons on the same fixture |
| Handles uncertainty | Correct simulated/controlled scenario labeled honestly | Blind retry hidden behind spinner |
| Saves time | Fair measured manual baseline including setup | Invented productivity percentage |
| Is accessible | Actual keyboard/zoom/screen-reader observations | A checklist or framework choice |

## Summary skeleton, not final copy

1. The specific workshop-creator problem and audience.
2. What the actually implemented product does when a venue/date label/URL changes.
3. Actual OAuth/API operations and how confirmed drafts are repaired.
4. The distinctive fact-to-span interaction and what is deliberately left unchanged.
5. Measured evidence if any, with honest limits.
6. Next improvement based on observed friction, not a list of promised features.

Write the final version only after the build can support it. Avoid future-tense feature claims presented as completed work.

## AI and provenance disclosure

This planning package was prepared with AI assistance. A future project must disclose the actual development/design/model tools used and human decisions accurately. No runtime AI is currently required by the product design. Do not invent a model benchmark or imply the application uses AI merely because development was assisted.

## Do not submit if

OAuth or real edits are unverified, the live app is inaccessible, source content rights are unresolved, a critical authorization test fails, the video shows fabricated execution, or final permission is missing. A polished repository does not override those gates.
